## 旅行场景与目标用户

### 先说清楚我们不做什么

酒店赛道已经被切得很干净了：

- **选哪家** —— 八维 PK、评分排行（已有作品在做）
- **这单花多少钱** —— 含早重算、套餐现金支出（已有作品在做）
- **按预算筛** —— 候选过滤、证据不足不拍板（已有作品在做）

这三格都有人站着了。「住回本」只占最后一格：

> **用户已经决定（甚至已经付款）住这家酒店之后，从入住 15:00 到退房 12:00 的这段 45 小时怎么过。**

### 四类真实用户

| 用户 | 他的原话 | 产品要回答的 |
| --- | --- | --- |
| 囤货后悔型 | "双十一囤了 2 晚含早套餐，周五去能用吗？" | 有效期、可用星期、加价日、早餐够不够 |
| 带娃补差型 | "孩子 1.25 米，套餐写 1.2M 以下" | 免票成不成立、补差多少 |
| 纯宅躺平型 | "我根本不打算出门，这酒店值不值？" | 步行半径里几处真能走到、酒店内有什么权益 |
| 商务误判型 | "看名字有江景就订了两晚" | 周边是否 0 处可达、45 小时会不会变成困在房间 |

### 45 小时的口径（当场算给你看）

```
2026-11-27 15:00 入住 → 2026-11-29 12:00 退房 = 45.0 小时
  其中 16.0 小时是睡眠（两晚 × 8h）
  真正可安排的是 29.0 小时清醒时间 ← 我们要交代的就是这 29 小时
```

## 我做了什么

### 1. 把套餐的营销文案拆成条件（这是全产品最有价值的一步）

飞猪 `search-marriott-package` 返回的 `sellPoint` 是唯一有信息量的字段，而真正让人到店翻车的条件全埋在里面：

> 【核心地段】…，【超值套餐】标准房2晚连住含2早+单人午市套餐+不含积分房晚，
> **【预订须知】有效期至2027年3月31日，周二至周四需加价200元**

> 自助餐主题随时令更新，**周三至周日通用 周末不加价**，星厨团队 数百种美食不限量畅吃，
> **每位成人可携带一位1.2M以下儿童**

这些条件标题里看不到、价格里看不到。我们把它们解析成结构化字段：晚数、早餐份数、可用星期窗口、加价日与金额、有效期、儿童身高上限、是否含会员积分房晚、权益清单。

三条硬规矩：

1. **每个字段必须带原句证据**，没有证据不落地
2. **有歧义不猜**——"2 晚连住含 2 早"里"2 早"是总量还是每晚？标进 `ambiguous`，交给规则层判待核
3. **解析不出来就写进 `missing`**，不拿"一般来说"补位

### 2. 排一条带证据等级的时间轴

固定锚点：15:00 入住、23:00–07:00 睡眠、11:30–12:00 退房。套餐权益按语义偏好时间落位（晚餐 18:30、早餐 07:30、下午茶 15:00、午市遇到退房则自动提前到 10:00）。周边 POI 只放步行可达的，且**全部标「待核」**。

每一格只有三种状态：**已核实 / 待核 / 留白**。放不下的进 `rejected`，不静默丢弃；剩下的空档显式留白，不硬塞。

### 3. 九条确定性校验（模型不许改算式）

| 规则 | 检查内容 |
| --- | --- |
| R1 | 套餐有效期 vs 离店日期 |
| R2 | 可用星期 vs 入住日 |
| R3 | 加价日 × 间夜数 → 加价金额 |
| R4 | "周末不加价"是否被触发 |
| R5 | 儿童身高 vs 免票门槛 |
| R6 | 早餐份数 vs 成人 × 晚数（含歧义标注） |
| R7 | 边际成本（房费已沉没，只算增量；"起价"不给总价） |
| R8 | 步行半径：haversine × 1.3 绕行系数 ÷ 4.5km/h |
| R9 | 餐段权益 vs 12:00 退房 |

### 4. 同一套规则跑出的两个真实结论

**样例 A：杭州滨江世融艾美酒店 + 自助晚餐套餐 + 1.25m 儿童**

- 风险：套餐限 1.2M 以下儿童，同行 1.25m → 免票不成立，补差金额接口未返回 → 待核
- 风险：步行 1200m 内 **0 处可达**，最近的虎跑公园直线 2722m、**约 47 分钟步行**
- 时间轴：29 小时清醒里只有 **3.2 小时**有证据支撑，**25.8 小时留白**
- **结论：这家酒店在数据上给不出任何可核验的周边体验，不值得为 staycation 住两晚**

**样例 B：杭州薇花园民宿（西湖店，满觉陇）+ 无套餐**

- 步行 1200m 内 **3 处**：少年儿童公园 196m（约 3 分钟）、虎跑公园 1136m、太子湾公园 1181m
- 时间轴：1.2 小时已核实 + 6.0 小时待核（3 个 POI 各 2 小时）+ 21.8 小时留白
- **结论：这是真正"住进去就能玩"的酒店，但 POI 开放时间接口不返回，因此全部标待核，不编造**

> A 和 B 的差别不是"我更推荐谁"，而是**同一套规则给出的两种事实**。
> 产品最锋利的能力是否证，不是安排。

### 5. 交付物

一页手机全屏可读的入住手册：结论四宫格 → 9 条核验（按严重度排序，每条带原句）→ 45 小时时间轴 → 步行半径榜 → 套餐原文 → 数据边界声明。

## 数据边界（写在作品里，而不是藏起来）

飞猪 FlyAI 接口实测**不返回**：房型、设施清单、设施营业时间、押金与退改、早餐单价、POI 开放时间；`search-hotel` 的 `score` / `review` 实测全为 null（这与其他参赛作品的踩坑记录一致）。

因此本项目：**不做评分排行、不编造设施、不编造开放时间、不给"起价"总价**。拿不到的一律进「待核」，并给出核实路径（打酒店电话 / 看订单页 / 飞猪详情页）。

这不是保守，是产品的第一性选择：**宁可交一份有黄色"待核"块的手册，也不交一份看起来完整、到店才发现错的手册。**

## 踩坑记录

1. **文档是删节版，实跑才作数**：`search-poi` 文档示例里没有坐标，真实返回却有 `latitude/longitude`、`listRank` 和几百字 `description`；反过来 `search-hotel` 文档写了 `score`/`review`，实测全是 null。所有设计都按实跑字段定，不按文档定。
2. **`search-hotel` 没有评分** → 直接砍掉了"做排行"的念头，也砍掉了和头部作品正面撞车的风险。
3. **"起价"是陷阱**：`￥998起/2晚` 的"起"意味着不能给总价，最初版本曾试图加总，后来改成只报缺口和待核。
4. **自己写的时间轴会骗自己**：第一版把 POI 塞满 45 小时，看起来漂亮但全是编的时间。改成"宁可留白"之后，样例 A 直接给出了"不值得住两晚"的结论，反而更有说服力。
